How it works

Outbound only. Through the proxy. Out the other side.

Agent sandboxes can't accept inbound connections and usually reach the internet only through an allowlisting, TLS-intercepting proxy. localcloud dials out to a relay you control, and your browser meets it there.

  1. 1

    Dial out, never in

    The client opens a WebSocket to your relay — through HTTPS_PROXY, trusting the sandbox's custom CA. If the proxy mangles WebSockets, it quietly falls back to plain HTTPS long-polling.

  2. 2

    Get a URL that sticks

    The relay hands out a friendly name like sunny-otter-x7k2. Sandbox naps, reconnects, daemon restarts — the URL stays the same, and visitors see a waiting page in the meantime.

  3. 3

    Your dev server sees localhost

    Requests stream down the tunnel with Host and Origin rewritten to localhost:3000, so Vite, Next.js and Angular host checks pass and HMR websockets just reconnect.

Features

Small tool. Sweats the details.

Everything an agent (or a human) needs to put a preview in front of someone, and nothing it has to be told twice.

Gets out of locked-down sandboxes

Honors HTTPS_PROXY / NO_PROXY and picks up intercepting CAs from NODE_EXTRA_CA_CERTS, SSL_CERT_FILE and friends. WebSocket first, HTTPS long-poll when that's all the proxy allows. localcloud doctor tells you exactly which path works.

$ npx localcloud-cli doctor
  • egress proxy proxy.internal:3128
  • extra CA certificates loaded
  ✓ relay reachable in 84ms
  ✓ websocket transport works (fastest)
  ✓ https long-poll transport works (fallback)

Background mode for agents

localcloud start 3000 prints the URL and returns, so the agent's turn keeps going. With no port, it watches and auto-shares every dev server that starts listening.

HMR keeps working

WebSocket upgrades are tunneled end to end. Save a file in the sandbox, watch the page update on your phone.

Host checks just pass

No allowedHosts, no --host 0.0.0.0. The dev server thinks it's talking to localhost. Need the real host? --host-header preserve.

Stable, friendly URLs

Same URL across reconnects, or pick your own with --name my-app → my-app.example.com.

Waiting pages, not error pages

Server still booting or sandbox reconnecting? Visitors get a calm page that reloads itself the moment it's back.

Nothing is answering on port 3000 yetWaiting… this page refreshes by itself.

MCP server built in

localcloud mcp exposes share_port, list_shared, stop_sharing and auto_share as tools.

Teaches your agents

localcloud init writes instructions to AGENTS.md / CLAUDE.md and a Claude Code SessionStart hook. Zero prompting after that.

Private when you want

--protect adds an access key to the link, --auth user:pass adds basic auth, and a relay token decides who may tunnel at all.

Setup

Set it once per repo. Every agent gets it.

Point localcloud at your relay, commit, and allow the relay's domain in the agent's network settings. That's the whole ritual.

  1. In your repo, run once and commit the result:

    $ npx -y localcloud-cli init --relay https://example.com

    Writes localcloud.json, AGENTS.md, CLAUDE.md and a SessionStart hook in .claude/settings.json:

    "SessionStart": [{ "matcher": "startup", "hooks": [{
  "type": "command",
  "command": "if [ \"$CLAUDE_CODE_REMOTE\" = \"true\" ]; then npx -y localcloud-cli start || true; fi"
}]}]

  2. In the environment's Network access settings, add your relay domain to the allowed domains.

  3. Start a session. Every dev server Claude starts gets a public URL, and Claude hands it to you instead of a localhost link.

  1. Commit the agent instructions (Codex reads AGENTS.md):

    $ npx -y localcloud-cli init --relay https://example.com

  2. In the Codex environment, turn on agent internet access and allow your relay domain.

  3. Optionally add auto-sharing to Environment → Setup script:

    $ npx -y localcloud-cli start

    Either way, AGENTS.md tells Codex to run npx -y localcloud-cli start <port> whenever it starts a server, and to give you the URL.

  1. Commit the agent instructions:

    $ npx -y localcloud-cli init --relay https://example.com

  2. Auto-share from .cursor/environment.json, so background agents boot with it:

    {
  "install": "npm install",
  "start": "npx -y localcloud-cli start"
}

  3. Ask the agent to run the app. It replies with an https://…example.com link you can open anywhere.

  1. Commit the agent instructions:

    $ npx -y localcloud-cli init --relay https://example.com

  2. In Devin's Machine setup, add a startup command:

    $ npx -y localcloud-cli start

  3. Now npx -y localcloud-cli ls lists every dev server Devin has running, with its public URL.

  1. Anywhere with Node 18.18+ — Copilot coding agent, Jules, Replit, a CI job, your laptop:

    $ export LOCALCLOUD_RELAY=https://example.com
$ npx -y localcloud-cli start            # auto-share every dev server
$ npx -y localcloud-cli run -- npm run dev # or wrap one command
$ npx -y localcloud-cli url 5173          # just print the URL

  2. Agent speaks MCP? Add it as a tool server (localcloud init --mcp writes this to .mcp.json):

    { "mcpServers": { "localcloud": {
  "command": "npx", "args": ["-y", "localcloud-cli", "mcp"]
} } }

  3. Scripting it? Every command takes --json.

Self-host

Your own relay in 60 seconds.

There's no hosted public relay yet — and for previews of unreleased work, owning the box in the middle is a feature. The relay is one small Node process with one dependency.

  1. Run it. Anywhere that can take inbound HTTPS.
  2. Point DNS. example.com and *.example.com at it, with TLS from your platform or Caddy. No wildcard? It falls back to single-domain routing.
  3. Connect. localcloud init --relay https://example.com and commit.

  • Fly.io
  • Render
  • Railway
  • Caddy

  routing: subdomain (*.example.com)
  clients: open to anyone (set LOCALCLOUD_RELAY_TOKEN to restrict)

# or, without Docker
$ LOCALCLOUD_DOMAIN=example.com npx -y localcloud-cli relay

FAQ

Questions, answered.

Is there a hosted relay I can use right now?

Not yet. Today you run your own — it's a single container, and the steps above take about a minute. Once you have one, commit it with localcloud init --relay … and nobody on the team (human or agent) configures anything again.

Why not just use ngrok or cloudflared?

On your laptop, they're great. Inside an agent sandbox, outbound traffic usually goes through an allowlisting proxy that terminates TLS with its own CA, and anything that isn't plain HTTPS gets dropped. localcloud is designed for exactly that path, runs from npx without an account, and ships the agent-side glue (background mode, MCP, AGENTS.md, hooks).

My agent says the relay is blocked. What now?

The sandbox's network policy doesn't allow your relay's domain yet. Add it to the environment's allowed domains (in Claude Code on the web: environment → Network access), then run npx -y localcloud-cli doctor to confirm both transports.

Who can open my preview?

Anyone with the URL — names are random, so they're hard to guess, but not secret. Use --protect for a link that carries an access key, --auth user:pass for basic auth, and set LOCALCLOUD_RELAY_TOKEN on the relay to control who can create tunnels.

Do I need to change my Vite / Next.js / Angular config?

No. localcloud rewrites Host, Origin and Referer so the dev server believes it's being visited on localhost. Keep it bound to localhost on its usual port.

What happens when the sandbox goes to sleep?

The client reconnects and reclaims the same URL. Until it does, visitors see a friendly “reconnecting” page that reloads itself, instead of a scary error.

What does it cost?

localcloud is free and MIT-licensed. The only cost is wherever you run the relay — many platforms have a free or near-free tier that's plenty for previews.
